## 1. Ringkasan hasil

Enam endpoint baru melengkapi modul project: `GET/POST /api/projects/:projectId/milestones`, `PATCH .../milestones/:milestoneId`, `GET/POST .../tasks`, dan `PATCH .../tasks/:taskId`. Semua request divalidasi dengan Zod `.strict()`, tanggal diterima hanya `YYYY-MM-DD` yang benar secara kalender, `milestoneId` wajib milik project yang sama, dan `handbookItemId` wajib merujuk item handbook yang ada. `lessonId` tetap diterima sebagai UUID mentah tanpa lookup atau penyentuhan modul learning. Ringkasan handbook di-response diambil dari tabel shared schema tanpa mengimpor file internal modul handbook.

## 3. Perubahan utama

- `GET /api/projects/:projectId/milestones`: daftar milestone milik project, diurutkan berdasarkan `createdAt`; project tidak ada → `404`.
- `POST .../milestones`: `{ title, targetDate?, status? }` → `201`; default `status: "Planned"`, `targetDate: null`.
- `PATCH .../milestones/:milestoneId`: partial `{ title?, targetDate?, status? }` → `200`; `targetDate: null` mengosongkan tanggal; milestone dari project lain → `404`.
- `GET .../tasks`: `{ data: [...] }` dengan filter opsional `milestoneId` dan `status` sesuai kontrak; filter `milestoneId` lintas project → `404`; response memuat ringkasan `handbookItem` bila referensi ada.
- `POST .../tasks`: `{ title, description?, milestoneId?, status?, dueDate?, handbookItemId?, lessonId? }` → `201`; default `status: "Todo"`.
- `PATCH .../tasks/:taskId`: partial field yang sama → `200`, termasuk mengosongkan `milestoneId`, `handbookItemId`, `lessonId`, dan `dueDate` dengan `null`.
- Validasi tanggal menolak format selain `YYYY-MM-DD` dan tanggal kalender yang tidak ada (mis. `2026-02-30`); nilai dikonversi ke `Date` UTC sebelum ditulis ke kolom `date` Drizzle, dan terbaca kembali persis `YYYY-MM-DD`.
- Status memakai enum schema: milestone `Planned|In Progress|Completed`; task `Todo|In Progress|Done|Blocked`.
- Helper `assertProjectExists`, `assertMilestoneInProject`, dan `assertHandbookItemExists` memakai `AppError(404, "NOT_FOUND", ...)`; helper `resolveHandbookReferences` dipakai ulang oleh detail project P3.1 agar tidak ada duplikasi logika.
- Tidak ada endpoint delete, assign user, notifikasi, perubahan schema, atau import modul internal handbook/learning.

## 7. Risiko atau masalah yang ditemukan

- **Referensi lintas modul tanpa FK.** `handbookItemId` dan `lessonId` tetap UUID eksplisit sesuai schema; keberadaan handbook dicek di handler, tetapi bukan constraint database. Tidak ada migrasi pada slice ini.
- **`lessonId` sengaja tidak berguna.** Ini keputusan sadar sesuai instruksi "lewati learning", bukan bug tersembunyi.
- **Belum ada pagination `meta`.** Endpoint daftar mengikuti pola `{ data: [...] }` seperti P3.1/P2; kontrak masih menyebut `meta` dan tetap `Proposed`.
- **Belum ada automated backend test.** Modul project kini delapan handler; smoke manual menjadi semakin rapuh dan disarankan mendapat slice hardening terpisah bila disetujui.
- **Risiko drift helper resolusi handbook.** Helper kini dipakai P3.1 dan P3.3; perubahan kebijakan status handbook perlu diperiksa di kedua jalur.
- **Working tree tetap uncommitted.** Perubahan Phase 1, 2, dan 3 belum di-commit; tidak ada reset/checkout/stash destruktif.
